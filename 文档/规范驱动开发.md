# 核心矛盾

传统 TDD/BDD 是:
> 人类驱动开发

Vibe Coding 是:
> AI 高速生成代码

问题在于:

> AI 最擅长 快速生成
> 
> AI 最不擅长 长期保持系统的一致性

如果 Vibe Coding 没有 TDD/BDD 来约束, 项目后期会"快速腐烂"

# TDD
TDD（Test-Driven Development，测试驱动开发）

核心思想：

>先写失败的测试，再写实现代码，最后重构。

经典循环：

1. Red（红）
    写一个失败的测试
2. Green（绿）
    写最少代码让测试通过
3. Refactor（重构）
    在测试保护下优化代码结构

也就是：

> 测试 -> 实现 -> 重构

# BDD
BDD（Behavior-Driven Development，行为驱动开发）

它其实是：

> TDD 的“业务语言升级版”。

BDD 不强调：

> 测试代码

而强调：

> 业务行为

## BDD 关注：
> 系统应该表现出什么行为

而不是：

> 某个类怎么实现

## BDD 常见格式

经典 Given / When / Then：
```
    Given 某种前提
    When 发生某种行为
    Then 应该得到某种结果
```
例如：
```
    Given 用户是会员
    When 购物车金额达到100
    Then 应该享受9折优惠
```
这就是 BDD 风格。

# Vibe Coding 下的 TDD
传统 TDD:

* 人写测试
* 人写实现
* 人重构

Vibe Coding:

* 人定义意图
* AI 写测试
* AI 写实现
* AI 重构

# 关键
> 测试 = AI 的约束系统

# AI 的天然问题
## 1. 漂移 (Drift)
今天生成:
```C#
IPriceService.Calculate();
```

明天突然变成:
```C#
PriceManager.Compute();
```

因为 AI 没有真正长期记忆

## 2. 幻觉式重构

AI 很喜欢:
> 顺手优化一下

然后:
> 整个系统炸了

它会:

* 改命名
* 改参数
* 改职责
* 改调用链

甚至:
> 把你没要求改的东西一起改了

测试就是:
> 给 AI 戴上约束

## 3. AI非常容易过度工程化

特别容易:
> 抽象工厂 + 泛型仓储 + 中介者 + 事件总线

直接给你一套大架构

但:
> 业务可能只有两百行

TDD 会逼 AI:
> 只实现当前需求

# Vibe Coding 推荐的模式

不是纯 TDD

而是:

> BDD -> Test -> Code -> Refactor

即:

> 规范驱动

## 第一步: BDD Scenarios

先写行为
```gherkin
Feature: 会员折扣

    Scenario: 普通会员打9折
    Given 用户是普通会员
    And 购物车金额为100
    When 进行价格计算
    Then 最终金额应为90
```

这一步定义"世界规则"

## 第二步: AI生成测试

让 AI:
> 根据BDD场景生成测试

## 第三步: AI 实现代码

现在 AI 才允许写业务代码

否则:
> AI 会边写边发明需求

## 第四步: 自动回归

AI 每次改代码:
> 必须跑测试

否则:
> 你根本不知道它偷偷改了什么

# BDD 在 AI 时代的重要性
因为:
> BDD 本质是"自然语言契约"

AI 对自然语言理解远强于:
> 人类写的架构图

所以未来的趋势是:
> BDD -> AI -> Code

而不是:
> 人类手写所有实现

# 未来的 AI Coding 结构
大概率会变成:
```
    Spec（行为规范）
        ↓
    BDD Scenarios
        ↓
    AI Generate Tests
        ↓
    AI Generate Code
        ↓
    Auto Evaluation
        ↓
    Refactor
```

"代码"反而越来越不重要

真正重要的是:
* 规则
* 行为
* 契约
* Evaluation
* Guardrail
