# 基础模型相关
## LLM（Large Language Model）
__LLM（大语言模型）__，本质上是一种能够“理解和生成人类语言”的 AI 模型。

> LLM = 根据上下文预测下一个最可能出现的词

比如你输入：

> 今天天气很好，我想去

模型会预测下一个词可能是：

* 散步 ✅
* 公园 ✅
* 吃饭（也可能）

它不是“真正理解世界”，而是基于概率在“接话”。

### LLM 的代表模型有哪些？

常见的 LLM：

* GPT-4 / GPT 系列
* Claude
* Gemini

## Token
模型处理文本的最小单位。

不是“字符”。

例如：

| 文本                 | Token 数 |
| :------------------- | :------- |
| hello                | 1        |
| 你好                 | 可能 1~2 |
| “Clean Architecture” | 多个     |

Token 会影响：

* 成本
* 上下文长度
* 推理速度

## Context Window(上下文窗口)
模型一次能"记住"的Token数量

例如：

* 128k
* 1M
* 2M

## 多模态 (Multimodal)
> 多模态 = 同时处理多种数据形式（模态）的 AI

### 什么是“模态（Modal）”

模态就是信息的“表现形式”，比如：

* 📝 文本（Text）
* 🖼️ 图片（Image）
* 🎧 音频（Audio）
* 🎥 视频（Video）
* 🎮 动作 / 交互（Action）


# AI 应用架构相关

## Prompt

> “Prompt”（提示词）是你和 AI（尤其是大语言模型）沟通的输入指令。

简单说：

👉 你写给 AI 的话，就是 prompt；AI 的回答，是对 prompt 的响应。

例如：

* 你问：“今天天气怎么样？” → 这是一个 prompt
* 你说：“帮我写一篇关于环保的作文” → 也是 prompt
* 你输入一段代码让 AI 帮你修改 → 还是 prompt

### 一个好的 Prompt 通常包含什么
1. 目标(Goal/Intent)
   > 这是最关键的，没有这个就是“无约束随机输出”。
   例子：
   * ❌ “帮我写点东西”
   * ✅ “帮我写一个番茄钟 + ToDo 联动功能的设计方案”
   如果目标不明确，AI 就不知道你想要什么样的输出，结果就会很随机。
2. 上下文（Context）
    > 你的背景、环境、限制条件
    例子:
    * 技术栈（WPF / .NET / Unity）
    * 项目阶段（MVP / 重构 / 架构设计）
    * 使用工具（Claude Code + DeepSeek）
    不给上下文，AI 就只能用它“训练时学到的知识”来回答，可能和你项目实际情况不符。
3. 约束（Constraints）
    > 限制 AI 的输出范围
    常见约束：
    * 输出格式（Markdown / 代码 / 表格）
    * 技术限制（必须用 MVVM / CQRS）
    * 性能要求（低内存 / 高并发）
    * 风格（简洁 / 架构化 / 可落地）
    例子：
    * 用 Clean Architecture + CQRS 设计，不要写伪代码，要给出目录结构
    没有约束的 Prompt，AI 可能会写出“理论化、泛泛而谈”的答案，而不是“具体可执行”的方案。
4. 输入数据(Input)
    > 你提供给 AI 的原始数据
    比如:
    * 代码
    * 文档
    * 错误信息
    * SQL
    例子：
    * 这是我的 UserService.cs 文件，帮我分析它的职责和改进点
    不给输入数据，AI 就只能基于它“训练时学到的知识”来回答，可能和你项目实际情况不符。
5. 输出格式(Output Format)
    > 你希望 AI 的回答是什么样子的
    例子：
    * Markdown 分层结构
    * 目录树
    * Mermaid 图
    * 分步骤执行清单
    不指定输出格式，AI就会按“默认作文模式”输出，看着优雅，实际上没法用。
6. 角色/视角（Role, 可选）
    > 让 AI 用什么身份思考
    这会影响“深度”和“风格”。
    例子:
    * 你是一名有经验的 C# 开发工程师
    * 你是一个架构师，专注于 Clean Architecture
    * 你是一个资深的 Unity 开发者
    * 你是一个技术文档写手
    * 你是一个代码审查专家
    * 你是一个软件设计模式专家
    这其实是“隐式约束”，会影响推理路径，不只是风格那么简单。
7. 评估标准（Evaluation Criteria, 可选）
    > 你会用什么标准来评估 AI 的回答
    例子：
    * 是否符合 Clean Architecture 原则
    * 是否满足性能要求
    * 是否可读性高
    * 是否有实际可执行的步骤
    这会让 AI 在生成答案时“心里有数”，知道什么样的回答才是“好”的。


标准 Prompt 模板
```
目标：
我想实现 XXX

上下文：
- 技术栈：
- 当前架构：
- 已有问题：

约束：
- 必须使用：
- 不要使用：
- 性能要求：

输入：
（代码 / SQL / 描述）

输出格式：
- 用 Markdown
- 给出目录结构
- 分步骤说明

评估标准：
- 优先 XXX
- 避免 XXX
```

一个好 Prompt =
> 目标 + 上下文 + 约束 + 输入 + 输出格式 +（可选）评估标准

### Prompt的常见类型
#### 1. 指令型（Instruction）

最常见

> 帮我写一个对象池

#### 2. 示例型（Few-shot）

给例子，让 AI 模仿
```
输入：1+1
输出：2

输入：2+2
输出：
```

#### 3. 角色扮演（Role Play）

比如：

* 扮演《赛博朋克:边缘行者》中的 Lucy
* 扮演《命运石之门》中的 牧濑红莉栖

👉 用来控制风格和语气

#### 4. 思维链（Chain of Thought）
让 AI 分步骤思考

> 请一步一步分析这个问题

### Prompt 的重要性
因为：

👉 AI 的能力上限 ≈ Prompt 的表达能力

同一个模型：

* 垃圾 Prompt → 垃圾结果
* 好 Prompt → 专家级输出

这也是现在所谓的：

👉 Prompt Engineering（提示词工程）

### 高质量问法
```
你是一名有经验的 C# 开发工程师，

我正在开发一个企业内部管理系统，
需要实现用户管理模块（支持用户的增删改查、角色分配等功能）

需求：
- 支持用户的增删改查
- 支持角色分配与权限管理
- 遵循 DDD + Clean Architecture
- 区分 Data / Domain / Application / Infrastructure

请输出：
1. 模块划分（目录结构）
2. 核心类设计（User、Role、UserService 等）
3. 关键交互流程（新增用户、分配角色）
```

## System Prompt
系统级 Prompt。

优先级最高。

例如：

* “你是高级架构师”
* “使用中文”
* “禁止输出 markdown”

## RAG
__RAG = Retrieval-Augmented Generation（检索增强生成）__

> 先查资料，再让 AI 回答

### 普通 LLM（不带 RAG）
* 只能用训练数据
* 不知道你项目里的代码
* 容易胡编（幻觉）

### 带RAG
流程是：
```
你的问题
   ↓
先去“你的知识库”里查相关内容
   ↓
把查到的内容 + 问题 一起喂给 AI
   ↓
AI 基于这些“真实资料”回答
```
👉 本质：

> LLM + 私有数据 = 可控 AI

### RAG 的核心流程

#### 1️⃣ 文档切分（Chunking）
把你的资料拆成小块

比如：

* 一个类 = 一个 chunk
* 一段设计说明 = 一个 chunk

因为模型不能一次吃无限内容。

Chunk 太小：

* 上下文断裂

Chunk 太大：

* 检索不精准

这是 RAG 的关键调参点之一。

#### 2️⃣ 向量化（Embedding）
把文本变成“向量”（数学表示）

用类似：

* OpenAI 的 embedding 模型
* 或其他 embedding 服务

👉 结果：
```
"WeaponInstance 是武器运行时对象"
↓
[0.123, -0.88, ...]
```

#### 3️⃣ 存入向量数据库（Vector DB）
存 Embedding 的数据库。

常见：

* FAISS
* Pinecone
* Weaviate

“找到语义最相近的内容

#### 4️⃣ 查询（Retrieval + Generation）
当你问：

> WeaponInstance 应该怎么设计？

流程：
```
问题 → 向量化 → 在向量库里找最相似的内容 → 取 Top K
→ 拼到 Prompt → 让 LLM 回答
```

### RAG 实际做的事
#### Step 1：找到相关内容

比如检索到：

* “WeaponInstance 是聚合根”
* “Ability 通过组合提供能力”
* “Runtime 不依赖 Data”

#### Step 2：拼成 Prompt
```
基于以下上下文：

[文档片段1]
WeaponInstance 是聚合根...

[文档片段2]
Ability 提供扩展能力...

问题：
WeaponInstance 是否应该持有 AbilityRuntime？
```

#### Step 3：LLM 回答

👉 这时候回答会：

* 不胡编
* 和你架构一致
* 有上下文

### RAG 的价值
#### 1️⃣ 解决“AI不知道你项目”的问题

👉 这是你现在最需要的

#### 2️⃣ 替代传统知识库

相比：

* Wiki
* Notion
* Confluence

👉 RAG 可以：

> 直接问，而不是自己找

#### 3️⃣ 极其适合你这种开发场景

你可以做：

__🔥 用于代码理解__
* “这个模块干嘛的？”
* “这个类应该放哪一层？”

__🔥 用于架构一致性__
* “这个设计是否符合 DDD？”

__🔥 用于自动生成代码__
* 基于你现有架构生成新模块

# Agent相关

## Agent

> Agent = 能“感知 → 决策 → 行动”的 AI 实体

### 和普通 AI 的区别
#### ❌ 普通 AI（Chat）
* 你问一句，它答一句
* 不会主动做事
* 不记目标

#### ✅ Agent
* 有目标（Goal）
* 会自己拆任务
* 会调用工具
* 会持续执行直到完成

### Agent 的核心结构
一个 Agent 本质上由 4 个部分组成：
#### 1️⃣ 目标（Goal）

👉 它要完成什么

例如：

* “设计一个武器系统”
* “修复这个 bug”
#### 2️⃣ 思考（Reasoning）

👉 它如何做决策

通常通过 Prompt + LLM 实现：

> 我下一步应该做什么？
#### 3️⃣ 记忆（Memory）

👉 它记住什么

包括：

* 当前上下文
* 历史步骤
* 中间结果
#### 4️⃣ 行动（Action）

👉 它能做什么

通常通过工具实现（比如结合 MCP）：

* 读文件
* 写代码
* 调 API

#### 总结构图
> Goal → 思考 → 行动 → 结果 → 再思考（循环）

### 常见的Agent有哪些？

#### AI 编程 Agent
* Claude Code
* Codex
* Cursor
* GitHub Copilot

👉 特点：

* 读代码
* 改代码
* 理解项目结构

#### 自动执行型 Agent
* AutoGPT
* BabyAGI

👉 特点：

* 自动循环执行任务
* 自己拆任务
* 自己继续做

👉 问题：

* 不稳定
* 容易“跑偏”

#### 多 Agent 协作框架（偏工程）
* LangChain
* CrewAI

👉 用来：

* 搭建 Agent 系统
* 编排 Workflow
* 管理多个 Agent

#### 工作流 + Agent
* n8n
* Zapier

👉 用来：

* 自动处理业务流程
* 调用 API
* 做自动化任务



## MCP
MCP = Model Context Protocol（模型上下文协议）

> 让 AI “安全、标准化地访问外部能力（工具 / 数据）”的一种协议

### 为什么需要MCP
LLM 本身的限制:

* 不能直接访问你的代码库
* 不能调用本地工具（比如 Git、Unity）
* 不能访问数据库 / 文件系统
* 只能“聊天”

MCP把这些能力标准化

### MCP负责的事情

> 可以认为MCP是AI的"插件系统协议"

```
AI（LLM）
   ↓
通过 MCP
   ↓
调用外部工具 / 获取数据
   ↓
再回来继续回答
```
### MCP的核心组成
#### 1. Resources (资源)
> 提供"可读数据"

例如：
* 文件（代码、Markdown）
* 数据库
* 文档

#### 2. Tool Calling (工具)
> AI 可以“调用”的能力

例如：

* 执行命令
* 修改文件
* 调用 API

#### 3. Prompts (提示模板)
> 预定义好的 Prompt

预定义好的 Prompt

比如：

* “分析代码结构”
* “生成 Unity 脚本”

## 多Agent（Multi-Agent）
> 多 Agent = 多个 AI 各司其职，像团队一样协作

### 对比
#### 单 Agent
* 一个 AI 干所有事
* 既分析需求、又写代码、又做架构

问题：

* 容易混乱
* 上下文爆炸
* 质量不稳定

#### 多Agent的流程
把任务拆开：
```
[需求分析 Agent]
        ↓
[架构设计 Agent]
        ↓
[代码生成 Agent]
        ↓
[代码审查 Agent]
```

> 每个只做一件事 → 更稳定、更专业

### 核心思想
#### 1.分工（Specialization）
每个 Agent 有：

* 明确职责
* 专属 Prompt
* 专属能力

#### 2.协作（Collaboration）
Agent 之间：

* 传递结果
* 相互校验
* 迭代优化

#### 3.编排（Orchestration）
需要一个“调度者”：

> 谁先做？谁后做？谁失败重试？

# 推理与生成相关

## Inference（推理）

模型运行生成结果的过程。

训练结束后：

> 真正“回答问题”的阶段。

## Temperature
生成文本时的一个“随机性控制参数”

Temperature 越低：
* 越理性
* 越稳定
* 越保守
* 更像程序
Temperature 越高：
* 越发散
* 越随机
* 创造性强
* 更容易胡说

可以理解为:
> “模型在选择下一个词时，到底有多敢‘乱来’。”

## Hallucination（幻觉）
模型编造不存在的信息。

LLM 最大问题之一。

RAG 的目的之一：

> 减少幻觉。


## Fine-tuning(微调)
> 让模型“改变行为”，而不是“临时记住信息”

### 举个非常具体的例子
你想让 AI：

* 用你定义的 API 风格写代码
* 遵守你那套 Clean Architecture 命名
* 输出固定格式

### 对比用 RAG
```
每次都要：
- 读取 docs/
- 提示规则
```
👉 麻烦 + 不稳定

### 对比用 Fine-tuning
你喂数据：
```
输入：写一个查询商品分页
输出：严格按你的 CQRS + 命名
```
训练后：

👉 模型天然就会这么写

### 技术本质

Fine-tuning 做的事情其实是：

> 调整模型参数（weights）

也就是：

> 改变神经网络内部的概率分布

比如：
```
P("GetProductPageQuery") ↑
P("ProductService.GetPage") ↓
```

### 什么时候该用 Fine-tuning

#### ✅ 适合：
* 固定输出格式（如 JSON、协议）
* 特定代码风格（你的 Clean Arch）
* 行业语气（客服 / 法律 / 医疗）

#### ❌ 不适合：
* 文档问答（→ RAG）
* 动态知识（→ RAG）
* 工具调用（→ Agent / workflow）

# AI工程化相关
## Workflow
> Workflow = 把多个 AI 步骤串起来执行

Claude Code 的 workflow, 本质是:
```
输入（Prompt / 上下文）
        ↓
Agent理解意图
        ↓
决定是否执行某些步骤
        ↓
调用工具 / 执行任务
        ↓
根据结果继续或停止
```

而是更接近：
“由 Agent 决策驱动的动态执行流程”

你写一个 workflow：
```
1. 读取 docs/
2. 分析需求
3. 生成代码
4. 运行测试
5. 修复 bug
```

你以为是这样执行的：
```
1 → 2 → 3 → 4 → 5 （固定流程）
```

但实际上更像：
```
if (需要上下文) → 读取 docs/
if (问题是代码生成) → 生成代码
if (检测到错误) → 运行测试 + 修复
否则 → 跳过
```

### ClaudeCode的Workflow特点
#### 1. workflow 是“建议”，不是“强制”

Claude Code 会：

* 参考你的 workflow
* 但不会盲目执行

👉 它会“优化路径”

#### 2. execution 是“按需触发”

比如：



| 情况       | 会不会执行测试 |
| :--------- | :------------- |
| 只是问问题 | ❌ 不执行      |
| 生成代码   | ✅ 可能执行    |
| 修 bug     | ✅ 一定执行    |

#### 3. Agent 会“跳步骤”
比如：

* 已经有结果 → 不再分析
* 文档没用 → 不读 docs
* 没 bug → 不修复

👉 这叫 决策式执行（decision-based execution）

### 如何强制执行workflow
#### 方法1：写死 Prompt
```
必须严格按照以下步骤执行，不得跳过：
1. ...
2. ...
```
👉 但依然不能100%保证

#### 方法2：拆成多轮任务（推荐）
```
Step1: 只做分析
Step2: 再生成代码
Step3: 再测试
```
👉 用你熟悉的“用例驱动（UseCase）”思路

#### 方法3：外部 orchestrator（高级）
比如：

自己写一个调度器
控制 Claude Code 调用顺序

👉 这才是“真正 workflow 控制权”

# 部署与推理相关

```
客户端
```

* 隐私

# 工程实践里最重要的几个概念
推进团队做 AI 工程化，最关键的其实只有这几个：

| 领域                | 核心             |
| :------------------ | :--------------- |
| Prompt              | 如何描述任务     |
| Context Engineering | 如何组织上下文   |
| RAG                 | 如何接知识库     |
| Agent               | 如何自动执行     |
| Workflow            | 如何组织步骤     |
| Tool Calling        | 如何接外部能力   |
| Evaluation          | 如何评估结果     |
| Guardrail           | 如何限制 AI 行为 |
