# LLM
__LLM（Large Language Model，大语言模型）__，本质上是一种能够“理解和生成人类语言”的 AI 模型。

> LLM = 根据上下文预测下一个最可能出现的词

比如你输入：

> 今天天气很好，我想去

模型会预测下一个词可能是：

* 散步 ✅
* 公园 ✅
* 吃饭（也可能）

它不是“真正理解世界”，而是基于概率在“接话”。

## LLM 的代表模型有哪些？

常见的 LLM：

* GPT-4 / GPT 系列
* Claude
* Gemini


# Agent

> Agent = 能“感知 → 决策 → 行动”的 AI 实体

## 和普通 AI 的区别
### ❌ 普通 AI（Chat）
* 你问一句，它答一句
* 不会主动做事
* 不记目标

### ✅ Agent
* 有目标（Goal）
* 会自己拆任务
* 会调用工具
* 会持续执行直到完成

## Agent 的核心结构
一个 Agent 本质上由 4 个部分组成：
### 1️⃣ 目标（Goal）

👉 它要完成什么

例如：

* “设计一个武器系统”
* “修复这个 bug”
### 2️⃣ 思考（Reasoning）

👉 它如何做决策

通常通过 Prompt + LLM 实现：

> 我下一步应该做什么？
### 3️⃣ 记忆（Memory）

👉 它记住什么

包括：

* 当前上下文
* 历史步骤
* 中间结果
### 4️⃣ 行动（Action）

👉 它能做什么

通常通过工具实现（比如结合 MCP）：

* 读文件
* 写代码
* 调 API

### 总结构图
> Goal → 思考 → 行动 → 结果 → 再思考（循环）

## 常见的Agent有哪些？

### AI 编程 Agent
* Claude Code
* Codex
* Cursor
* GitHub Copilot

👉 特点：

* 读代码
* 改代码
* 理解项目结构

### 自动执行型 Agent
* AutoGPT
* BabyAGI

👉 特点：

* 自动循环执行任务
* 自己拆任务
* 自己继续做

👉 问题：

* 不稳定
* 容易“跑偏”

### 多 Agent 协作框架（偏工程）
* LangChain
* CrewAI

👉 用来：

* 搭建 Agent 系统
* 编排 Workflow
* 管理多个 Agent

### 工作流 + Agent
* n8n
* Zapier

👉 用来：

* 自动处理业务流程
* 调用 API
* 做自动化任务


# Prompt

> “Prompt”（提示词）是你和 AI（尤其是大语言模型）沟通的输入指令。

简单说：

👉 你写给 AI 的话，就是 prompt；AI 的回答，是对 prompt 的响应。

例如：

* 你问：“今天天气怎么样？” → 这是一个 prompt
* 你说：“帮我写一篇关于环保的作文” → 也是 prompt
* 你输入一段代码让 AI 帮你修改 → 还是 prompt

## 一个好的 Prompt 通常包含什么
你可以用一个简单结构来理解：

1. 角色（Role）

让 AI 知道自己是谁

> 你是一名 C# 开发工程师

2. 任务（Task）

你要它干什么

> 设计一个用户管理模块

3. 上下文（Context）

你的背景信息

> 这是一个企业内部管理系统，需要支持用户的增删改查

4. 约束（Constraints）

限制条件

> 使用 C#，遵循 DDD + Clean Architecture

5. 输出格式（Output）

你希望它怎么回答

> 用分层结构说明，并给出目录结构

组合起来就是：

```
你是一名 C# 开发工程师，
帮我设计一个用户管理模块，

背景：
- 企业内部管理系统
- 需要支持用户的增删改查

要求：
- 使用 C#
- 遵循 DDD + Clean Architecture

输出：
- 给出目录结构
- 解释各层职责
```

## Prompt的常见类型
### 1. 指令型（Instruction）

最常见

> 帮我写一个对象池

### 2. 示例型（Few-shot）

给例子，让 AI 模仿
```
输入：1+1
输出：2

输入：2+2
输出：
```

### 3. 角色扮演（Role Play）

比如：

* 扮演《赛博朋克:边缘行者》中的 Lucy
* 扮演《命运石之门》中的 牧濑红莉栖

👉 用来控制风格和语气

### 4. 思维链（Chain of Thought）
让 AI 分步骤思考

> 请一步一步分析这个问题

## Prompt 很重要
因为：

👉 AI 的能力上限 ≈ Prompt 的表达能力

同一个模型：

* 垃圾 Prompt → 垃圾结果
* 好 Prompt → 专家级输出

这也是现在所谓的：

👉 Prompt Engineering（提示词工程）

## 高质量问法
```
你是一名有经验的 C# 开发工程师，

我正在开发一个企业内部管理系统，
需要实现用户管理模块（支持用户的增删改查、角色分配等功能）

需求：
- 支持用户的增删改查
- 支持角色分配与权限管理
- 遵循 DDD + Clean Architecture
- 区分 Data / Domain / Application / Infrastructure

请输出：
1. 模块划分（目录结构）
2. 核心类设计（User、Role、UserService 等）
3. 关键交互流程（新增用户、分配角色）
```

# RAG
__RAG = Retrieval-Augmented Generation（检索增强生成）__

> 先查资料，再让 AI 回答

## 普通 LLM（不带 RAG）
* 只能用训练数据
* 不知道你项目里的代码
* 容易胡编（幻觉）

## 带RAG
流程是：
```
你的问题
   ↓
先去“你的知识库”里查相关内容
   ↓
把查到的内容 + 问题 一起喂给 AI
   ↓
AI 基于这些“真实资料”回答
```
👉 本质：

> LLM + 私有数据 = 可控 AI

## RAG 的核心流程

### 1️⃣ 文档切分（Chunking）
把你的资料拆成小块

比如：

* 一个类 = 一个 chunk
* 一段设计说明 = 一个 chunk

### 2️⃣ 向量化（Embedding）
把文本变成“向量”（数学表示）

用类似：

* OpenAI 的 embedding 模型
* 或其他 embedding 服务

👉 结果：
```
"WeaponInstance 是武器运行时对象"
↓
[0.123, -0.88, ...]
```

### 3️⃣ 存入向量数据库（Vector DB）
常见：

* FAISS
* Pinecone
* Weaviate

👉 用来做“语义搜索”

### 4️⃣ 查询（Retrieval + Generation）
当你问：

> WeaponInstance 应该怎么设计？

流程：
```
问题 → 向量化 → 在向量库里找最相似的内容 → 取 Top K
→ 拼到 Prompt → 让 LLM 回答
```

## RAG 实际做的事
### Step 1：找到相关内容

比如检索到：

* “WeaponInstance 是聚合根”
* “Ability 通过组合提供能力”
* “Runtime 不依赖 Data”

### Step 2：拼成 Prompt
```
基于以下上下文：

[文档片段1]
WeaponInstance 是聚合根...

[文档片段2]
Ability 提供扩展能力...

问题：
WeaponInstance 是否应该持有 AbilityRuntime？
```

### Step 3：LLM 回答

👉 这时候回答会：

* 不胡编
* 和你架构一致
* 有上下文

## RAG 的价值
### 1️⃣ 解决“AI不知道你项目”的问题

👉 这是你现在最需要的

### 2️⃣ 替代传统知识库

相比：

* Wiki
* Notion
* Confluence

👉 RAG 可以：

> 直接问，而不是自己找

### 3️⃣ 极其适合你这种开发场景

你可以做：

__🔥 用于代码理解__
* “这个模块干嘛的？”
* “这个类应该放哪一层？”

__🔥 用于架构一致性__
* “这个设计是否符合 DDD？”

__🔥 用于自动生成代码__
* 基于你现有架构生成新模块


# MCP
MCP = Model Context Protocol（模型上下文协议）

> 让 AI “安全、标准化地访问外部能力（工具 / 数据）”的一种协议

## 为什么需要MCP
LLM 本身的限制:

* 不能直接访问你的代码库
* 不能调用本地工具（比如 Git、Unity）
* 不能访问数据库 / 文件系统
* 只能“聊天”

MCP把这些能力标准化

## MCP负责的事情

> 可以认为MCP是AI的"插件系统协议"

```
AI（LLM）
   ↓
通过 MCP
   ↓
调用外部工具 / 获取数据
   ↓
再回来继续回答
```
## MCP的核心组成
### 1. Resources (资源)
> 提供"可读数据"

例如：
* 文件（代码、Markdown）
* 数据库
* 文档

### 2. Tools (工具)
> AI 可以“调用”的能力

例如：

* 执行命令
* 修改文件
* 调用 API

### 3. Prompts (提示模板)
> 预定义好的 Prompt

预定义好的 Prompt

比如：

* “分析代码结构”
* “生成 Unity 脚本”

# 多Agent（Multi-Agent）
> 多 Agent = 多个 AI 各司其职，像团队一样协作

## 对比
### 单 Agent
* 一个 AI 干所有事
* 既分析需求、又写代码、又做架构

问题：

* 容易混乱
* 上下文爆炸
* 质量不稳定

### 多 Agent
把任务拆开：
```
[需求分析 Agent]
        ↓
[架构设计 Agent]
        ↓
[代码生成 Agent]
        ↓
[代码审查 Agent]
```

> 每个只做一件事 → 更稳定、更专业

## 核心思想
### 1.分工（Specialization）
每个 Agent 有：

* 明确职责
* 专属 Prompt
* 专属能力

### 2.协作（Collaboration）
Agent 之间：

* 传递结果
* 相互校验
* 迭代优化

### 3.编排（Orchestration）
需要一个“调度者”：

> 谁先做？谁后做？谁失败重试？


# 多模态 (Multimodal)
> 多模态 = 同时处理多种数据形式（模态）的 AI

## 什么是“模态（Modal）”

模态就是信息的“表现形式”，比如：

* 📝 文本（Text）
* 🖼️ 图片（Image）
* 🎧 音频（Audio）
* 🎥 视频（Video）
* 🎮 动作 / 交互（Action）



# Workflow
> Workflow = 把多个 AI 步骤串起来执行

Claude Code 的 workflow, 本质是:
```
输入（Prompt / 上下文）
        ↓
Agent理解意图
        ↓
决定是否执行某些步骤
        ↓
调用工具 / 执行任务
        ↓
根据结果继续或停止
```

而是更接近：
“由 Agent 决策驱动的动态执行流程”

你写一个 workflow：
```
1. 读取 docs/
2. 分析需求
3. 生成代码
4. 运行测试
5. 修复 bug
```

你以为是这样执行的：
```
1 → 2 → 3 → 4 → 5 （固定流程）
```

但实际上更像：
```
if (需要上下文) → 读取 docs/
if (问题是代码生成) → 生成代码
if (检测到错误) → 运行测试 + 修复
否则 → 跳过
```

## ClaudeCode的Workflow特点
### 1. workflow 是“建议”，不是“强制”

Claude Code 会：

* 参考你的 workflow
* 但不会盲目执行

👉 它会“优化路径”

### 2. execution 是“按需触发”

比如：



| 情况       | 会不会执行测试 |
| :--------- | :------------- |
| 只是问问题 | ❌ 不执行      |
| 生成代码   | ✅ 可能执行    |
| 修 bug     | ✅ 一定执行    |

### 3. Agent 会“跳步骤”
比如：

* 已经有结果 → 不再分析
* 文档没用 → 不读 docs
* 没 bug → 不修复

👉 这叫 决策式执行（decision-based execution）

## 如何强制执行workflow
### 方法1：写死 Prompt
```
必须严格按照以下步骤执行，不得跳过：
1. ...
2. ...
```
👉 但依然不能100%保证

### 方法2：拆成多轮任务（推荐）
```
Step1: 只做分析
Step2: 再生成代码
Step3: 再测试
```
👉 用你熟悉的“用例驱动（UseCase）”思路

### 方法3：外部 orchestrator（高级）
比如：

自己写一个调度器
控制 Claude Code 调用顺序

👉 这才是“真正 workflow 控制权”


# Fine-tuning(微调)
> 让模型“改变行为”，而不是“临时记住信息”

## 举个非常具体的例子
你想让 AI：

* 用你定义的 API 风格写代码
* 遵守你那套 Clean Architecture 命名
* 输出固定格式

## 用 RAG
```
每次都要：
- 读取 docs/
- 提示规则
```
👉 麻烦 + 不稳定

## 用 Fine-tuning
你喂数据：
```
输入：写一个查询商品分页
输出：严格按你的 CQRS + 命名
```
训练后：

👉 模型天然就会这么写

## 技术本质

Fine-tuning 做的事情其实是：

> 调整模型参数（weights）

也就是：

> 改变神经网络内部的概率分布

比如：
```
P("GetProductPageQuery") ↑
P("ProductService.GetPage") ↓
```

## 什么时候该用 Fine-tuning

### ✅ 适合：
* 固定输出格式（如 JSON、协议）
* 特定代码风格（你的 Clean Arch）
* 行业语气（客服 / 法律 / 医疗）

### ❌ 不适合：
* 文档问答（→ RAG）
* 动态知识（→ RAG）
* 工具调用（→ Agent / workflow）
